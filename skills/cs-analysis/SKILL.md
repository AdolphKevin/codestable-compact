# `$cs-analysis` — 分析一次实际任务中的知识使用

用户主动调用时，结合当前任务对话和可读取的项目记录，判断 CodeStable 是否帮助
任务、是否遗漏约束或增加无效负担。交付一份自包含 Markdown 报告，供用户带回
`codestable-compact` 讨论改进。报告描述这次使用，不替项目验收，也不自动改造工具。

## 调用与边界

```text
$cs-analysis
$cs-analysis 分析刚完成的库存修复任务，重点看知识检索和卡片粒度
$cs-analysis 将报告保存到 /tmp/cs-analysis.md
```

- 默认在当前对话输出完整报告；用户要求保存时才写报告文件，并提供文件链接。
  不覆盖已有报告，除非用户明确要求覆盖。报告保存在用户指定位置，不进入 Wiki。
- 不自动触发，不加入 `$cs` 的开发流程，不初始化、重建或更新消费项目知识库。
  不调用 `learn`，不补写任务记录，不重建索引，不修改代码、配置或 Git 状态。
- 不收集或导出原始对话、模型完整回答、完整命令输出、完整差异、秘密或个人数据。
  报告只保留必要事实摘要；使用项目代称和相对路径，敏感名称用一致代称替换。
  用户自己把报告带回维护项目，不自动上传、发消息或建立持续监控。
- 分析本身不是新的开发任务，不为生成报告再执行 `$cs` 的任务前后写入流程。

## 以任务发生时的依据为准

先确定用户指的是哪一项逻辑任务。同一目标的连续修复和补充验收属于同一任务；
对话包含多个独立目标且无法判断时，再向用户澄清。任务未完成也可以分析，写明
观察截至哪个阶段，不把尚未到达的知识回写时机判断为遗漏。

从可见对话建立紧凑的事件顺序：用户目标、第一次知识查询、相关实现或验证、
后续范围变化、知识写入预览与应用、最终检查。只记录判断需要的事件，不复制聊天。

优先利用：

- 实际调用及返回摘要，尤其是查询中的卡片编号、版本、匹配原因和证据提示；
- 任务中公开表达的设计选择、实现位置和已执行验证；
- 对应任务记录、关联卡片、取代关系及相关摘要；
- 当时使用的技能版本或规则；无法取得时标明未知，不拿最新版规则追责旧任务。

有需要才读取任务涉及的文件、测试和知识正文。已知任务编号时，可用共享工具的
只读 `task-files --task-id` 缩小记录范围；不要扫描无关聊天或其他项目。

可以补充运行只读检查，但先找到实际可用的 `cs` 技能目录并执行其
`scripts/bootstrap.py --root <project-root> --check`。当前格式可读时，再按需运行
`status`、`doctor`、`audit`、`drift`、`task-files` 或 `brief`，使用共享工具实际支持的参数。
这些是可选辅助，不要求为每份报告执行全部检查。工具或知识库不可用时，仍依据
对话生成有限范围的报告，不初始化、不迁移、不把读取失败等同于知识不存在。

**补跑的查询或检查只说明分析时的状态。** 把它们标为“分析时补充检查”，不能据此
声称任务当时展示过某张卡片。卡片后来新增或升级，也不能证明原查询漏掉了它。
当前文件与检查结果不能代替任务时的版本或测试结果。

对话压缩、历史工具结果不可见或记录未关联时，写明无法确认。看不到命令不等于
没有执行；没有前后状态证据不能声称只读操作确实零写入。先判断实际行为是否由
用户明确要求，而不是机械认定偏离默认步骤就是错误。

## 判断哪些行为值得保留或改进

以下是分析视角，不是自动分类算法、逐项打分表或必须发现问题的清单。选择与任务
有关的视角，由执行助手结合业务含义、用户约束和实际产物判断；不适用就说明原因。

| 视角 | 判断依据 |
|---|---|
| 读取时机与范围 | 知识是否在关键选择前可用；真实路径或职责明显变化后，是否仍沿用不相关的旧范围 |
| 相关性与完整性 | 返回内容是否服务本任务，关键共享约束和例外是否一起呈现；有任务时版本依据才判断具体漏项 |
| 实际使用 | 卡片是否可追溯地影响范围、设计、实现、测试或评审；仅展示、引用编号或结果碰巧一致不证明作用 |
| 真假与冲突处理 | 是否区分已接受要求、已验证行为、提议和历史；证据变化提示是否被理解，是否静默选边或刷新声明 |
| 任务记录 | 同一连续任务是否合理聚合，记录是否反映最终结果与真实验证；没有新卡片本身不是问题 |
| 分类与导航 | 归属是否帮助未来使用者查找，主题和范围能否补充其他视角；合理的分类差异不等于错误 |
| 卡片粒度 | 是否构成可独立复用、检索完整、可独立维护的知识单元；条件、例外、失败行为可共同表达一个保证 |
| 沉淀与演进 | 是否只保留稳定结论；有无同义重复、过早固化、错误取代或失去来源；结论不变时是否合理复用或更新 |
| 操作负担 | 实际重复查询、预览失败或填写工作是否有具体原因和收益；不因步骤数多就断定多余，不因步骤齐全就断定合理 |

卡片粒度同时考虑拆分与合并：拆开会丢失关键条件就保留整体；内容回答不同问题、
被独立复用或各自变化时，才有拆分理由。不要按字数、句子数或分类交叉自动拆卡。
提出调整时指出本任务中的实际查找或维护影响；只有假设时，将其列为待验证建议。

## 从观察到可验证的改进

先给每项重要依据一个报告内编号。对每个发现分别写清楚：

- 看到了什么、依据在哪里，以及这次任务中已观察到的影响；
- 哪些原因已经确认，哪些只是推测，哪些资料缺失；
- 更可能涉及工具实现、技能说明、执行助手判断、项目知识内容，还是正常的用户选择。

原因归属可以有多个候选；消费项目看不到工具源码时不要编造具体函数或根因。
没有可追溯影响时，写“作用无法确认”，而不是“知识无用”。实际结果与卡片一致
也不能单独证明卡片带来了改进，不推测没有 CodeStable 时会发生什么。

值得带回维护项目的建议应包含触发条件、期望行为、最小改动方向，以及可匿名复现
的情境和验收观察。复现分为“已发生的情况”和“建议验证的情况”；业务内容不能
公开时保留结构与边界，删去敏感细节并说明哪些细节不可提供。

单次失败先作为有范围的发现，不直接扩大为全局规则。已经合理的行为也记录下来，
以便后续改造保留它们。不强凑发现数量，不输出没有依据的评分或总体成功率。
如使用次数、耗时或比例，只统计有可见来源的数据并注明分母和范围。

按 [报告格式](references/report-format.md) 组织最终报告。生成后检查报告脱离当前
对话仍能读懂：包括任务摘要、已知版本、证据摘要、观察限制、发现和验证建议。
报告是供维护者核对的分析上下文，不作为消费项目的新知识卡片或自动修改指令。
