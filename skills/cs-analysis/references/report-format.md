# 报告格式

使用下面的结构生成自包含 Markdown。说明文字替换为实际内容；没有发现问题时
明确写出，不保留空的发现模板。重点以依据和影响为主，不强求每个视角都有条目。

## 报告头与结论

```markdown
# CodeStable 任务使用分析报告

- 报告格式：cs-analysis/1
- 分析日期：实际日期与时区
- 项目代称：匿名项目名
- 任务摘要：紧凑描述目标、主要交付物和当前完成状态
- 已知版本：任务使用的 CodeStable 版本；cs-analysis 版本或来源。未知分别注明。
- 可见范围：完整任务 / 部分对话 / 仅记录；列出具体缺失部分
- 总体判断：合理 / 有改进项 / 存在明确问题 / 证据不足

用一段话说明判断和最主要依据。存在明确问题不代表整个工具不合理；证据不足
也不代表任务执行失败。
```

总体判断是这次观察的总结，不是工具评级。发现问题和已有合理行为可以同时成立。

## 依据与经过

```markdown
## 依据摘要

| 编号 | 来源与时间范围 | 可核查的事实摘要 | 限制 |
|---|---|---|---|
| E1 | 当前任务对话：首次知识查询 | 实际查询范围、返回的相关结论；已知则带卡片编号和版本 | 未展示的内容无法判断 |
| E2 | 对应任务记录：相对路径、任务编号和版本 | 最终结果、验证和知识处置 | 当前记录可能晚于任务中的查询 |

## 关键经过

仅保留与判断有关的事件及先后顺序，用 E 编号关联依据。不编造精确时间、
轮次或命令。分析时补跑的命令单独列出，不能混入原任务经过。
```

依据摘要应包含理解发现所需的事实，不仅是本地文件链接。“助手声称通过”与
“看到了测试通过结果”分别描述。真实秘密完全移除，不以部分掩码保留。

## 合理行为与发现

```markdown
## 值得保留的行为

描述具体行为、作用和 E 编号。没有充分依据时说明尚无法确认。

## 发现与改进

### F1：具体问题或机会

- 判断：已确认问题 / 有限依据下的改进机会 / 待验证假设
- 观察：发生了什么，关联 E 编号
- 影响：本次已经观察到的后果；潜在后果另行标明
- 原因归属：工具实现 / 技能说明 / 执行判断 / 项目知识 / 用户选择 / 无法确认
- 原因依据与缺口：哪些已经核查，哪些尚不能确定
- 建议方向：最小且有范围的改动，或保持现状
- 匿名复现：已发生的前置知识、查询范围、执行行为与结果；必要时用结构化代称
- 验收观察：建议在什么任务或测试中观察什么结果，是否有需要保留的现有行为
```

为每个实际发现重复 F 条目。只有分类偏好不同、卡片较长、没有新增卡片或检查
步骤较多，不能直接标为问题。拆分建议说明拆分后完整性如何保持；合并建议说明
如何避免引入无关内容或重复结论。无法匿名复现时写清缺失依据，不捏造案例。

## 带回维护项目的上下文

```markdown
## 后续核对与改造范围

- 优先核对的发现：对应 F 编号和理由；无明确改造项时直接说明
- 需要补充的依据：仅列会改变判断的资料，不重复索取当前已可读取的信息
- 建议验证情境：标为未执行；不要把建议验证写成已经复现或通过
- 建议改动边界：需要检查的能力或说明，不猜测未读取的源码位置
- 必须保留的行为：来自已确认合理行为的约束

本报告仅覆盖上述任务与可见依据。由用户带回 codestable-compact 后，维护者
核对当前实现、历史版本和匿名复现，再决定优化范围。
```

报告正文已包含任务与依据摘要，无需把原始对话或完整日志作为附件。导出时只写
这份报告；默认对话输出时提供完整正文，方便直接复制作为维护项目的上下文。
