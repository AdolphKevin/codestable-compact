# 开发方法与知识归属

CS 可以与 MATT 等开发方法组合，也可以独立使用。开发方法选择实现、诊断、测试和
审查方式；CS 维护项目知识。这里复用 CS 的现有命令、任务记录和 11 类知识，不增加
方法专用的记录类型或知识库。

## 接入已初始化的项目

以 CS 为前提的方法包开始工作前，发现当前安装的 CS 技能并执行其只读预检。
CS 未安装、项目未初始化或格式不可用时，报告缺少的前提，停止该方法调用。
安装、初始化和重建是独立的用户目标，不能由方法调用代为触发。建立空目录也不能
代表已经完成 CS 初始化；初始化完成条件见 CS 主技能。

项目知识通过 `brief` 和 `documents read` 读取。源码、测试、用户当前需求和调研
所需的外部一手资料仍按任务查阅，不需要先复制进知识库。

## 同一任务共用知识流程

以 CS 主技能的逻辑任务边界和沉淀时机为准。规格、设计、实现、测试、审查等方法
连续处理同一用户目标时，共用当前任务上下文；在同一会话中，方法切换本身不要求
重复预检或重复 `brief`。新代理、恢复后缺少已读上下文，或任务范围和来源发生实质
变化时，按 CS 规则补读。临时研究材料可以作为当前任务输入，不另建长期知识副本。

普通开发任务结束后，由 CS 执行一次该逻辑任务的知识处置。已经存在任务记录时
沿用其编号更新，方法名称、调用次数和代理数量都不构成新任务。任务平台的需求与
协作记录继续保留，CS 任务记录保存紧凑结果和来源引用。写入、预览与应用步骤
直接遵循 CS 主技能，不在各开发方法中重述。

## 每份内容只有一个正文归属

| 内容 | 正文与记录方式 |
| --- | --- |
| 词汇、设计决策、项目规范 | 编辑原文件，通过 CS 登记和读取；记录此次变化，不再创建表达相同结论的卡片 |
| 需要长期检索的调研文档 | 保留一份交付文档并登记，沿用实际接受状态；引用不能把待确认发现变成已确认事实 |
| 普通任务的过程与结果 | 保存在同一条 CS 任务记录的紧凑结果中，不保存原始聊天、日志或第二份总结正文 |
| 原文与已有卡片未覆盖的长期经验 | 按现有分类、证据和复用要求写入 CS，已有等义结论优先复用或更新 |
| 尚未采纳的环境改进建议 | 留在会话或用户要求的报告中，不直接成为已确认知识 |

登记、章节引用、来源更新和已有重复内容的处理见[原文档和引用](documents.md)。
一份新原文已经可以通过 CS 检索时，无需仅为增加入口再建引用卡片；需要保留旧卡片
历史或明确章节关系时才使用引用。原文只覆盖部分结论时，仅将独立的新增经验写卡。
文字不同不代表结论不同，语义是否重叠需要结合原文审核；工具负责确定性的重复引用、
相同内容和版本校验。

例如，同一任务先用领域建模方法调整词汇表，再实现并审查代码：词汇表保存新定义，
CS 记录这次变更。若同时验证了原文未覆盖的事务约束，才为该独立结论建卡。再次调用
实现或审查方法仍更新原任务，不再写一份词汇解释或重复经验。

## 普通收尾与按需分析

普通开发任务完成知识记录即可，不固定调用任何复盘或分析技能。

- `matt-retro` 是按需的代理工作环境复盘，分析导航、指引、工具、信息获取和自动
  检查，交付改进建议。
- `cs-analysis` 仅在用户主动调用时分析 CS 的实际表现，交付供改进
  codestable-compact 使用的报告；它不执行消费项目的知识维护。

仅分析或提出建议不产生新的开发任务记录，也不触发 `learn`。建议经用户要求落实
为开发工作后，按实际用户目标判断是继续原任务还是新任务，并遵循普通 CS 流程。
项目范围明确、具备最终依据且能复用的环境经验也使用现有知识分类；通用建议不入库。
