# 检索、证据与治理验收

本文记录 当前格式的产品边界、重建规则和匿名验收案例。它描述
CodeStable 自身行为，不包含任何消费项目数据。

## 设计选择

### 检索分组

`brief` 把结果分为项目总览、分类摘要、当前卡片、提议卡片、显式历史和相关
任务。只有卡片使用 `brief.max_items` 与分类配额；分类摘要默认最多三条，既不
标记为已验证知识，也不计入 11 类覆盖。

卡片排序先比较匹配层级，再比较同层得分：

1. 精确仓库范围、精确路径或精确符号；
2. 路径或范围的父子关系；
3. 显式业务主题；
4. 标题、标签、路径或符号文本；
5. 正文文本。

没有采用“所有内容共享一个总分和配额”，因为分类摘要和历史任务会挤掉事实
卡片；也没有采用不可复现的向量聚类或外部检索服务，以保持本地 Markdown、
标准库和可审计排序。

每个结果返回 `match_reasons`。`brief.receipt` 绑定查询任务、范围、是否包含
历史、展示卡片 ID、状态、revision、来源和结论内容哈希。它的声明固定为
`displayed-only`，不能证明 Agent 阅读或采用了卡片。

### 卡片证据和未来复用

新卡片证据使用：

```json
{
  "kind": "implementation|test|contract|compatibility|accepted-decision",
  "artifact": "可定位产物",
  "result": "可核查结果",
  "supports": "该结果支持的卡片结论"
}
```

`verified` 必须至少有一项实现、测试、契约或兼容证据。仅有明确接受记录但尚
未实现或验证的决策使用 `accepted-decision` 和 `accepted`，不能伪装成
`verified`。

每个 current 卡片至少有两个不同的未来复用场景：

```json
{
  "change": "会触发复核的变更或任务",
  "actor": "未来实现者或评审者",
  "constraint": "届时约束的设计、实现或验证判断"
}
```

默认模板只提供 `__REPLACE__` 占位符，原样提交会失败。字符串启发式只拦截
明确占位或内置泛化模板；语义等义、证据是否充分等无法可靠自动判断的内容由
dry-run 候选和 `audit` 提醒，仍需人工审核。

### 知识使用证据

“展示”“阅读”“发挥作用”是三种不同事件：

- `brief` 回执只证明展示；
- 打开文件或引用编号最多证明阅读，不写入 `knowledge_use`；
- 只有卡片具体改变或约束设计、范围、实现、测试或评审，才记录使用。

`knowledge_use` 必须绑定卡片 ID 和实际读取的 revision，并记录类型、具体影响
与 `{kind, artifact, result, supports}` 证据。revision 已变化时，dry-run
要求重新检索和复核。`changed-design` 另需公开的修改前方案与最终方案；
`tested` 需稳定测试标识和不变量；`implemented` 需实现位置；`reviewed` 需审查
对象和具体发现或排除的问题。完整 Prompt、模型输出、完整 diff 和内部思维过程
不进入记录。

### 主题治理

主题是跨 11 类卡片的链接导航，不是第 12 类知识，也不复制卡片结论。配置必须
明确为：

- `disabled`：项目主动关闭主题；
- `manual`：允许部分覆盖，但空主题表属于未完成配置；
- `required`：验收当前卡片覆盖率不低于 `minimum_coverage`。

`topics suggest` 只从共享标签和仓库内范围前缀产生可复现候选，不写文件。
人工调整后的 `topics update` 必须 dry-run，再用绑定 payload、Wiki 状态和工作区
状态的令牌应用。批量赋值绑定卡片 revision；写入使用 Wiki 锁、恢复日志和回滚。
重命名或合并把旧定义写入 `wiki.topic_history`，新主题通过 `aliases` 和
`replaces` 继续解析旧卡片元数据。

主题参数只是检索提示，不是执行前置条件。Agent 不得从自然语言猜测主题编号；
应先用只读 `topics list` 获取规范名称，或者直接省略 `--topic`。未知主题会被忽略，
并返回可解释的近似名称建议；任务文本、路径、符号和仓库范围继续检索。写入卡片和
主题更新仍严格拒绝未配置名称，避免把拼写错误持久化。

项目直接复用当前 Skill 的知识工具。只读 `bootstrap.py --check` 检查数据格式与
命令是否可用；旧格式返回 `needs-rebuild`。没有用户授权时不清理数据，也不自动迁移。

### 统一只读验收

`audit` 分别报告：

- `structure`：`doctor` 的文件、索引、标识、取代关系、锁和事务检查；
- `current_references`：当前卡片的本仓库、相关仓库、外部未配置路径和保守符号扫描；
- `governance`：主题策略与覆盖、空或陈旧摘要、自由文本旧证据、泛化内容和可能等义的 current 卡；
- `delivery`：生成 Markdown 空白、维护仓库中生成 runtime 同步，以及 Git 知识回写；
- `business_truth: not-evaluated`：业务需求、实现行为和测试充分性仍由实现任务验收。

分段状态为 `pass`、`needs-attention`、`incomplete` 或 `not-applicable`。结构损坏、
当前引用问题、治理缺口或交付检查未完成时退出码为 1。没有扩张普通 `doctor`
的含义：普通绿色 doctor 仍只说明结构一致。

默认验收工作区；`audit --cached` 验收暂存内容，`audit --base <ref>` 验收分支
提交范围，三者沿用 `drift` 的知识回写规则。

没有采用“让 doctor 自动判断业务真相”，因为文件存在和符号文本命中无法证明
结论正确；也没有让历史卡片或未配置外部仓库阻断普通结构检查。

## 文件与完整重建

- 发行清单描述新库需要的完整文件集，项目复用共享知识工具。
- 用户明确授权后，完整重建替换目标 `.codestable`，不迁移旧配置、卡片、任务或旧目录；
  `.codestable` 以外的文件保持原位。先零写入预览，再按绑定内容和范围的计划执行。
- 本地缓存保存可重建目录和机器索引。Wiki 的稳定入口与人工正文纳入版本管理；
  `reindex --dry-run` 显示变化，`reindex` 恢复派生文件。
- 目录初始化不等于知识建立完成。必须从当前源码、测试和已确认需求生成知识，
  写入一条重建记录，并验证有代表性的查询和引用。详情见 [完整重建](rebuild.md)。

分类摘要可以添加：

```text
<!-- codestable:summary-review {"knowledge_hash":"<audit 输出>","reviewed_at":"<ISO-8601>"} -->
```

`audit` 比较当前卡片 ID、revision 和结论摘要生成的哈希。卡片变化、缺少标记或
超过复核期限时给出治理提醒；如果显式启用且健康的主题视图已经覆盖该分类，空
分类摘要可以由主题导航承担。

只支持当前配置格式（Schema 4）和本地缓存。旧数据必须完整重建，不进行格式转换或证据推测。

## 单文件发布与模块化维护

消费项目复用 Skill 中的 Python 标准库工具。维护源位于 `skills/cs/runtime_src`，
按公共格式、捕获校验、存储/索引、学习事务、检索、漂移、治理/验收和命令行分段。
`scripts/build_runtime.py` 确定性生成发布单文件并嵌入源摘要；`--check` 检测维护源与
发布资产不一致。测试始终执行生成后的真实发布文件。

## 匿名电商后端演进验收

以下仅为测试素材。初始方案把静音、内部备注和移动接收者规则放进实时网关。
已接受边界卡规定：业务服务决定通知语义和接收范围，传输网关只路由明确目标。

V3 任务的有效 `changed-design` 记录为：

- 修改前：静音、内部备注和移动接收者规则都放在实时网关；
- 最终方案：业务服务构造明确接收目标，实时和移动适配器只传输；
- 设计产物：匿名 `design/notification-v3.md`；
- 对应关系：该产物把接收者选择分配给业务服务，并从网关排除业务状态分支。

这证明旧边界改变了公开方案，而不只是被 `brief` 展示。随后新增的事务发件箱
决定是正交长期约束：业务记录和待发送通知同事务写入，投递器重试，消费者按
事件 ID 幂等。它有失败模式、替代方案、后果、适用范围、两个未来复用场景和
匿名原子写入测试，因此值得新建卡片；它不取代“业务服务决定接收范围”的边界。

长期保留当前业务边界、事务保证、失败语义、决策背景/理由/替代方案/后果、取代
链、有效兼容窗口、可定位证据和确实改变设计的知识使用记录。详细迁移步骤、失败
实验日志、临时兼容代码说明、重复任务、结束的发布清单和原始基准输出只归档并保
持可追溯；原始聊天、完整模型输出、完整 diff、秘密、用户或生产数据、单次报错和
未影响最终方案的猜测不沉淀。
